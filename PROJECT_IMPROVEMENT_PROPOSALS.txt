DISCVAULT / ПРЕДЛОЖЕНИЯ ПО УЛУЧШЕНИЮ ПРОЕКТА
Дата: 25.10.2026

Основа: анализ текущего кода React/TypeScript, Fastify, Prisma и PostgreSQL,
моделей игры, издания, экземпляра, объявлений, лута, ставок, сделок и оценок.
Учтён интерфейс каталога и карточек, проверенный в браузере в этом чате.
Это предложения и результаты чтения кода; изменения в приложение не внесены.

Проверки в рамках этого анализа:
- npm run typecheck — успешно.
- npm run typecheck:server — успешно.
- GET http://localhost:3001/api/health — status=degraded, database=down.
- Нагрузочные проверки, конкурентные запросы и интеграционные тесты с живой
  PostgreSQL не выполнялись. Указанные ниже риски гонок требуют воспроизведения.

Приоритеты:
P0 — до запуска настоящих сделок и работы нескольких пользователей.
P1 — ближайший этап: корректность, удобство и поддерживаемость.
P2 — развитие после стабилизации основных сценариев.
Размер работ: S — локальное изменение; M — несколько связанных модулей;
L — изменение модели данных или нескольких пользовательских сценариев.
Размер обозначает относительную сложность, а не обещанный срок.

ЧТО СТОИТ СОХРАНИТЬ

1. Разделение Game → Edition → Copy и MarketEntry: каталог отделён от конкретного
   физического экземпляра. Новый itemType расширяет маркет на отдельный лут.
2. Общие контракты и Zod-схемы в shared, строгие настройки TypeScript.
3. URL-состояние фильтров и drawer: доступны прямые ссылки и история браузера.
4. Сессии в httpOnly cookie, Argon2 для паролей, роли модерации, лимиты запросов.
5. Транзакции, version при ставках и дедупликация уведомлений уже существуют.
   Их нужно развивать и проверять, а не заменять общими рекомендациями с нуля.
6. Локальный режим и single-file сборка полезны для демонстрации и личной полки.
7. Согласованные иконки каталога и меню, компактные панели рейтингов,
   доступные названия счётчиков, общий ModalShell с управлением фокусом.

01. Явно разделить демо, гостевой просмотр и работу аккаунта
Приоритет: P0. Размер: M.
Код: src/context/AuthContext.tsx, src/hooks/useMarketEntries.ts,
     src/hooks/useGameCollection.ts, src/hooks/useNewsFeed.ts.
Наблюдение: маркет включает серверный режим только при наличии user.
Гость видит локальные объявления даже тогда, когда API доступен. При ошибке
первой загрузки аккаунта коллекция и маркет могут показывать локальные данные.
Предложение: публичные объявления получать с API независимо от входа;
локальное демо включать явно. При сбое серверной загрузки показывать ошибку
и повтор, сохраняя только данные того же аккаунта, если они уже загружены.
В интерфейсе дать короткий индикатор «Демо / Локально / Аккаунт».
Критерий: гость и авторизованный пользователь видят одну публичную ленту;
сбой API не подменяет личную коллекцию локальными записями.

02. Изолировать запросы и кэш разных аккаунтов
Приоритет: P0. Размер: M.
Код: src/hooks/useGameCollection.ts, src/hooks/useMarketEntries.ts,
     src/context/AuthContext.tsx.
Наблюдение: loadRemote не отменяет предыдущую загрузку при смене user.id;
remoteCopies/remoteEntries не привязаны к идентификатору владельца результата.
Старый ответ потенциально может прийти после переключения аккаунта.
Предложение: очищать личное состояние на границе сессии, применять результат
только при совпадении userId и поколения запроса, использовать AbortSignal.
Критерий: при искусственно задержанном ответе аккаунта A после входа в B
на экране B не появляются данные A.

03. Зафиксировать цену сделки атомарно
Приоритет: P0. Размер: M.
Код: server/src/deals/routes.ts, POST /market/:id/deals.
Наблюдение: цена читается до транзакции. Обновление объявления в транзакции
проверяет доступность, но не сравнивает прочитанную version или цену.
Гипотеза для теста: продавец меняет цену между чтением и созданием сделки,
а сделка фиксируется по старой цене.
Предложение: связать создание сделки с версией предложения; при конфликте
вернуть актуальную цену и запросить повторное подтверждение покупателя.
Критерий: конкурентное изменение цены не создаёт сделку с незаметно иной ценой.

04. Проверить границу закрытия аукциона внутри операции ставки
Приоритет: P0. Размер: M.
Код: server/src/bids/routes.ts, server/src/market/auctionCloser.ts.
Наблюдение: дедлайн проверяется до транзакции; условие updateMany для ставки
проверяет status, moderationStatus и version, но не само время окончания.
Предложение: определить точное правило момента приёма ставки и закрепить его
в атомарной проверке. Добавить тест «ставка одновременно с закрытием»,
включая два процесса API и повторный запуск закрытия.
Критерий: единственный результат торгов, одна сделка и согласованные уведомления;
ставка после принятого системой дедлайна не принимается.

05. Восстановить воспроизводимый запуск полного проекта
Приоритет: P0 для сетевого запуска. Размер: M.
Код: docker-compose.yml, server/.env.example, server/README.md.
Наблюдение: текущий health сообщает database=down. Последние возможности
добавили миграции оценок игр и категорий лута.
Предложение: проверить соответствие DATABASE_URL реально запущенной БД,
документировать один полный путь установки, миграций и seed на чистой машине.
Для рабочего размещения подготовить API, PostgreSQL, постоянное хранилище фото,
HTTPS, резервное копирование и проверку восстановления.
Критерий: новый разработчик получает health=ok и рабочую регистрацию по инструкции;
миграции проходят с чистой БД и с предыдущей схемы.
Примечание: статическая копия через Sites сама по себе не размещает Fastify и БД.

чтобы освободить уникальный marketEntryId. Повторная продажа поэтому возможна,
но отменённая договорённость исчезает из истории.
Предложение: хранить несколько попыток сделки по объявлению, отдельно ограничив
единственную активную попытку. Историю статусов и участников не удалять.
Критерий: отменённая сделка остаётся в истории обоих участников, повторная
продажа доступна, две активные сделки на один предмет невозможны.

23. Определить отдельную семантику обмена
Приоритет: P1. Размер: L.
Код: server/src/deals/routes.ts, shared/src/deals.ts, src/pages/AccountPage.tsx.
Наблюдение: создание сделки различает purchase и остальные объявления;
обмен использует ту же модель buyer/seller/amount.
Предложение: хранить предложение второй стороны, предметы обмена, доплату
при наличии и подтверждения участников. Не показывать оценочную цену обмена
как автоматически согласованную денежную покупку.
Критерий: обе стороны видят, что именно передают и получают; после изменения
состава обмена предыдущие подтверждения перестают действовать.

24. Унифицировать счётчики каталога на сервере

Критерий: число на карточке совпадает с количеством доступных предложений
в открываемой ленте, включая лут и при нескольких страницах результатов.

25. Разгрузить чтение маркета от закрытия всех просроченных аукционов

записей без явной сортировки, каждый лот закрывается отдельно.
Предложение: сортировать по дедлайну, отслеживать отставание, не допускать
наложения проходов, выделить worker при нескольких экземплярах API.
Сохранить идемпотентность и защиту version, а не полагаться только на один worker.
Критерий: API чтения сохраняет время ответа при большом числе завершений;
сбой одного лота не мешает остальным, повторный запуск не создаёт вторую сделку.

26. Усилить работу с изображениями и их жизненным циклом

Предложение: декодировать и проверять содержимое/размеры изображения, удалять
метаданные, создавать превью, связать файл с владельцем и объектом использования.
Очищать неподтверждённые и больше не используемые файлы по безопасному расписанию.
Для production явно определить политику отказа S3: локальный fallback разных
API-инстансов не является общим постоянным хранилищем.
Критерий: невалидный файл отклоняется, фото доступны после перезапуска/смены
инстанса, удаление одной ссылки не удаляет используемый другим объектом файл.

27. Сделать эксплуатацию наблюдаемой и ограничить доверие proxy
Приоритет: P1 перед публикацией. Размер: M.
Код: server/src/app.ts, server/src/server.ts, server/src/env.ts,
     server/src/auth/session.ts.
Предложение: доверять только реальному reverse proxy вместо безусловного
trustProxy=true, проверить Origin для мутаций с cookie и модель CSRF,
настроить request ID и метрики ошибок/задержек/очереди закрытия торгов.
Проверять сценарии блокировки пользователя, истечения сессии и лимитов запросов.
Логи не должны содержать пароли, cookie, токены и URL с секретами.
Критерий: подставленный X-Forwarded-For не обходит лимит при выбранной схеме
размещения; ошибку операции можно найти по request ID без раскрытия секретов.
Это задачи проверки конфигурации, а не заявление о доказанной эксплуатации.

Критерий: последующая правка объявления не меняет историю завершённой сделки;

30. Добавить регулярную проверку критичных сценариев
Приоритет: P1. Размер: M–L.
Код: package.json, scripts/market-items.test.ts, server/prisma/migrations/.
Наблюдение: есть тест категорий лута, но общей npm-команды тестов и полного
набора интеграционных проверок в просмотренной конфигурации нет.
Предложение: единые команды проверки типов, тестов и сборки; отдельная тестовая
PostgreSQL с миграциями. Браузерные сценарии проверяют поведение, а не CSS-классы.
Минимальный набор:
- регистрация, вход, выход и быстрая смена аккаунта при задержанных запросах;
- создание/редактирование каждого типа лута с изданием и без него;

Критерий: проверки запускаются одной документированной процедурой и воспроизводят
ошибки до их исправления; рабочие пользовательские данные в тестах не участвуют.
