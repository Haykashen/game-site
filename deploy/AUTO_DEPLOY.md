# Автоматическое обновление DiscVault

Подключённый стенд: Debian 12, SSH `root@89.125.42.120:22`,
папка `/opt/game-site`, Compose project `discvault`.
Окружение GitHub: `Haykashen/game-site` → `production`, разрешена ветка `main`.
Для Actions используется отдельный ключ, разрешённый владельцем VPS;
пароль сервера и серверный `.env` в GitHub не передаются.

Workflow: `.github/workflows/deploy.yml`. Публикация запускается после **push
в main**, а не после локального коммита. Pull request запускает только проверки.
Вручную запускать можно через Actions → Check and deploy DiscVault → Run workflow
для ветки main.

## Что происходит

1. В GitHub Actions ставятся зависимости и генерируется Prisma-клиент.
2. Миграции проверяются на отдельной пустой PostgreSQL в CI. Рабочая БД в этой
   проверке не участвует. Выполняются тесты, проверки типов и обе сборки.
3. Собираются API и web Docker-образы с тегом полного SHA коммита.
4. Архив с образами передаётся на VPS по SSH с проверкой host key и SHA-256 архива.
5. Сервер сверяет историю Prisma: применённые миграции нельзя изменять или удалять.
6. Если новых миграций нет, API ненадолго останавливается вместе с обработчиком
   аукционов. PostgreSQL и Caddy продолжают работать. В это время API недоступен.
7. Создаются PostgreSQL dump и архив локальных фотографий. Проверяется читаемость
   дампа и целостность gzip. Это не заменяет пробное восстановление на отдельной БД.
8. Меняются только контейнеры api/web. Именованные тома PostgreSQL, uploads и Caddy
   сохраняются. Сервисы db и volumes не пересоздаются.
9. Проверяется контейнер API, публичный HTTPS `/api/health` с `database=up`, главная
   страница. Успешный SHA записывается в `.deploy/current-revision`.

Деплои сериализованы и не отменяют выполняющийся деплой новым push. Устаревшие
коммиты, которые дождались запуска после более свежего main, пропускаются.
Дополнительно на VPS используется `flock`.

## Подключение к существующему VPS: один раз

Стенд уже должен работать через `docker-compose.prod.yml`, проект Compose —
`discvault`. Автоматизация не инициализирует пустую БД и не выполняет seed.
Если установка не найдена, она остановится до изменения приложения.

На VPS нужны Docker с современным Compose plugin (`up --wait`, `run --pull`),
Bash, flock, curl, gzip, tar, sha256sum и достаточное место под два поколения
образов и резервные копии. Debian 12 подходит при установленном Compose plugin.
Docker должен быть доступен SSH-пользователю без интерактивного sudo.
Доступ к Docker практически равнозначен администраторскому доступу к VPS:
для Actions используйте отдельный ключ и ограничьте его распространение.

Найти текущую папку установки (в консоли VPS):

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}'
docker inspect "$(docker ps -q --filter label=com.docker.compose.service=api --filter label=com.docker.compose.project=discvault)" --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'
```

Указанная папка должна содержать `.env` и `docker-compose.prod.yml` и быть
доступна SSH-пользователю для записи в `.deploy`. Допускаются абсолютные пути
из букв ASCII, цифр, `_`, `-` и `/`, например `/opt/discvault`.

Создайте отдельную пару ключей Ed25519 для GitHub Actions. Приватный ключ
добавьте непосредственно в секрет GitHub, не в репозиторий и не в чат.
Публичный ключ добавляется в `~/.ssh/authorized_keys` выбранного SSH-пользователя.
Для записи ключа полезны ограничения `restrict` (без туннелей и forwarding).
Изменение SSH-доступа — отдельный осознанный шаг владельца VPS.

В GitHub: Settings → Environments → production. Ограничьте deployment branches
веткой main. Для автоматического обновления без ручных разрешений не включайте
required reviewers. В этом environment создайте секреты:

| Секрет | Значение |
| --- | --- |
| `DEPLOY_HOST` | `89.125.42.120` |
| `DEPLOY_PORT` | SSH-порт, обычно `22`; пустое значение тоже означает 22 |
| `DEPLOY_USER` | SSH-пользователь, например `deploy`; нужно узнать фактический |
| `DEPLOY_PATH` | Реальная папка установки, например `/opt/discvault` |
| `DEPLOY_SSH_KEY` | Отдельный приватный ключ Actions |
| `DEPLOY_KNOWN_HOSTS` | Проверенная строка known_hosts сервера |

Host key проверяйте через доверенную консоль провайдера. Отпечаток на сервере:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
cat /etc/ssh/ssh_host_ed25519_key.pub
```

Для порта 22 строка `DEPLOY_KNOWN_HOSTS` имеет вид:
`89.125.42.120 ssh-ed25519 <публичный host key сервера>`.
Для другого порта: `[89.125.42.120]:<порт> ssh-ed25519 <ключ>`.
Это host key сервера, а не ключ из authorized_keys. Слепой ssh-keyscan во время
деплоя и отключение StrictHostKeyChecking не используются.

Пароль PostgreSQL и содержимое серверного `.env` в GitHub не требуются.
Сначала проверьте процедуру на копии стенда с восстановленными данными.
После настройки секретов и загрузки workflow в main выполните первый ручной
запуск без apply_migrations и проверьте Actions, сайт и резервные копии.

## Миграции БД

Автоматический push **не применяет новые миграции**. Если они обнаружены,
обновление останавливается до остановки рабочего API. Это намеренное поведение:
успешная сборка не доказывает безопасность SQL для существующих данных.

После проверки SQL и резервного копирования можно вручную запустить workflow
для main, отметив `apply_migrations`. Тогда после остановки API и резервных копий
выполнится `prisma migrate deploy`, затем повторная сверка журнала.
Нужно проверить миграции на восстановленной копии рабочей БД до такого запуска.
Проверка CI на пустой БД этого не заменяет.

Если миграция или запуск после неё не удались, API остаётся остановлен.
Нельзя автоматически вернуть прежнюю БД: это может скрыть частично применённый
SQL или удалить новые данные. Нужно проверить журнал `_prisma_migrations`,
совместимость старого кода и выбрать исправление либо восстановление вручную.
Для будущих изменений предпочтительны совместимые этапы: добавить поле,
обновить приложение, заполнить данные, отдельным релизом убрать старое поле.

В CI/CD API запускается напрямую `node dist/server.js`; миграции не спрятаны
в каждом рестарте контейнера. Обычный ручной запуск исходного Compose сохраняет
старое поведение CMD из Dockerfile: перед стартом выполняет migrate deploy.

## Резервные копии и откат

Копии хранятся на VPS в `<DEPLOY_PATH>/.deploy/backups/<UTC-время>-<SHA>/`:

- `database.dump` — PostgreSQL custom-format dump;
- `uploads.tar.gz` — файлы тома `/data/uploads`;
- `rollback.yml` — ссылки на сохранённые предыдущие образы;
- `target-revision` — SHA обновления;
- `health.json` — ответ успешной проверки, если она была выполнена.

Директории закрыты правами 0700, файлы создаются с umask 077. При использовании
внешнего S3 архив uploads не копирует объекты S3: для него нужен собственный backup.
Копии на том же VPS не защищают от потери самого сервера. Настройте отдельное
хранилище резервных копий и регулярно проверяйте восстановление.

При неудачном обновлении БЕЗ миграций скрипт пытается восстановить прежние
образы. Рабочую БД и uploads он при этом не восстанавливает и не изменяет.
Откат образов тоже может не удаться, например, при нехватке диска — проверяйте
результат в Actions и `/api/health`.

Пример ручного отката только кода (указать фактические пути):

```bash
cd /opt/discvault
docker compose --project-name discvault --env-file .env -f docker-compose.prod.yml -f .deploy/backups/ИМЯ_КОПИИ/rollback.yml up -d --no-deps --no-build --pull never --wait api web
```

Эта команда не откатывает схему БД. После миграций сначала проверьте совместимость.
Восстановление dump и фотографий выполняйте отдельно по проверенной процедуре,
остановив запись. Не восстанавливайте старый dump поверх новых действий пользователей.

Скрипт не выполняет `down -v`, `db push`, `migrate reset`, seed или prune.
Копии, архивы релизов и rollback-образы автоматически не удаляются. Контролируйте
место и настройте retention после выбора срока хранения; полный диск блокирует
обновление и может повлиять на работающую БД.

## Что обновляется автоматически

Код frontend/API, статические ресурсы и Caddyfile внутри web-образа.
Серверный `.env` и базовый `docker-compose.prod.yml` не перезаписываются;
конфигурацию инфраструктуры/volumes/портов меняйте отдельным проверенным шагом.
Git checkout на VPS не переключается: выполняемый SHA смотрите в
`.deploy/current-revision`, а код приложения находится в Docker-образах.

Автообновление предполагает один VPS, одну БД и отсутствие других процессов,
пишущих в эту БД во время backup. Несколько серверов требуют общей координации.
