# DiscVault: правила работы

Этот файл хранит устойчивые договорённости проекта для новых чатов. Актуальный код и документация определяют детали реализации; новые явные указания пользователя уточняют перечисленные ниже предпочтения. Не превращать этот файл в журнал релизов и переписку.

## Общение и границы задачи

- Общаться с пользователем по-русски, кратко и конкретно. Сообщать результат, выполненные проверки и реальные ограничения.
- Выполнять понятные обратимые изменения без повторных согласований. Разметка на скриншотах: стрелки показывают перенос или нужное положение, зачёркивания — удаление; учитывать сопровождающий текст.
- По умолчанию изменения делать локально. Просьба «макет на HTML/CSS» означает отдельный локальный прототип; переносить его в приложение после соответствующего указания.
- Просьбы «обнови сайт», «обновляй сайт» разрешают необходимые коммит, отправку изменений и развёртывание согласованных доработок. Доводить публикацию до проверенного результата.
- Не публиковать вместе с задачей посторонние изменения. Если рабочее дерево содержит чужие правки, сохранить их и определить состав своей задачи перед коммитом.
- Не запрашивать разрешение повторно, если оно уже дано для текущего действия. При обязательном отказе автоматической проверки объяснить конкретное заблокированное действие и причину; не обходить ограничение.
- Не выдавать локальную сборку за обновление сайта, запуск workflow — за успешный релиз, проверку кода — за визуальную проверку.

## Ориентиры в проекте

- Перед изменениями проверить `git status` и инструкции в затрагиваемых каталогах. Не использовать сбросы, очистку рабочего дерева или удаление пользовательских файлов для упрощения задачи.
- Клиент: React, TypeScript и Vite в `src/`; сервер — `server/`, общие модели — `shared/`. Точные версии и команды смотреть в `package.json` соответствующего workspace.
- Общие UI-компоненты искать в `src/components/ui/`, компоненты коллекции — рядом с реализацией коллекции. Сначала искать существующий компонент и его использования.
- Навигацию менять согласованно с маршрутами, мобильным меню и заголовками: ориентиры `src/app/navigation.ts`, `src/app/headerBanners.ts`, `src/App.tsx`.
- Группа «Сообщество» должна быть перед группой «Маркет».
- Не включать секреты, содержимое `.env`, дампы, пользовательские загрузки и временные артефакты в коммиты или этот файл.

## Единообразие интерфейса

- Использовать существующие компоненты вместо новой разметки и локальных CSS для того же элемента управления.
- Действия только с иконкой в заголовках карточек, включая редактирование, сохранение и закрытие, оформлять через `IconButton`.
- В одной группе действий сохранять одинаковые размеры, размер иконок, скругления, анимации hover/active, focus ring и disabled-состояния.
- Исправлять общий компонент, а не добавлять индивидуальные переопределения кнопок. Сохранять обоснованные смысловые различия элементов.
- Сохранять существующую палитру и систему иконок. Активный режим редактирования обозначать границей кнопки в брендовом цвете.
- Платформы показывать через `PlatformBadge`, количество в коллекции — через `CollectionCountBadge`, автора с рейтингом — через `AuthorRating`. Проверять и карточки списков, и страницу экземпляра.
- Текст платформы центрировать по обеим осям. Не ломать flex-выравнивание общего бейджа локальными стилями.
- Для поиска и выбора значений переиспользовать существующий `Combobox`; для комплектности — `CompletenessCombobox`, для цены — `MoneyInput`.
- Проверять светлую и тёмную темы и узкие экраны при изменении общих элементов. Отдельно указывать, какие визуальные проверки действительно выполнены, и какие проверки ограничились сборкой.

## Коллекция и страница экземпляра

- Страница экземпляра следует структуре страницы игры: галерея слева, реквизиты справа, действия и заметки ниже; на узком экране — последовательная компоновка.
- Порядок реквизитов: платформа, издание, регион, состояние, комплектность, дата покупки, цена покупки. Между строками сохранять разделители, в том числе между регионом и следующей строкой.
- Издание и регион в режиме просмотра показывать обычным текстом. Состояние показывать с `/10`, например `10/10`; не ломать отображение старых нечисловых значений.
- У названий комплектности показывать перевод в скобках, используя единый источник подписей.
- Состав комплекта и управление количеством располагать в правой колонке под реквизитами.
- Использовать один общий компонент управления количеством. На странице коллекции убрать его из карточек; разместить на странице экземпляра вместо прежнего блока «На полке».
- Нажатие на карточку коллекции открывает экземпляр. Вложенные кнопки, ссылки и переключатели фотографий выполняют своё действие без повторного открытия; сохранять доступность с клавиатуры.
- Заметки в карточках списка ограничивать двумя строками; на странице экземпляра показывать полностью.
- При добавлении игры год по умолчанию — текущий год из даты выполнения, доступный для исправления пользователем; не фиксировать конкретный год в коде.

## Редактирование экземпляра

- Кнопка «Редактировать» переключает режим при повторном нажатии. Без изменений выходить сразу; при изменениях предлагать сохранить, отказаться от изменений или продолжить редактирование.
- Значения реквизитов заменять полями на том же месте. Не создавать отдельную дублирующую форму ниже страницы.
- В режиме редактирования владельцу доступны состояние, комплектность, дата покупки, регион, цена и заметки; платформу и издание не делать редактируемыми без отдельной задачи.
- Удаление, добавление и перетаскивание миниатюр, а также текст с ограничениями загрузки показывать только владельцу в режиме редактирования.
- При отмене восстанавливать исходные значения, фотографии и их порядок. При ошибке сохранения сохранять черновик и показывать ошибку.
- Права владельца проверять на сервере, а не только скрытием кнопок.

## Фотографии

- У экземпляра использовать прикреплённые пользователем фотографии. Обложка издания не должна подменять их при наличии собственных фото.
- Несколько фото показывать галереей с индикаторами количества и активного изображения. У точек не должно быть общего тёмного фона, закрывающего фотографию.
- Сохранять переключение по точкам, движение между фотографиями на карточке и поддержку сенсорных экранов, предусмотренные текущей галереей.
- Миниатюры позволяют выбрать фото; в режиме редактирования — удалить, изменить порядок перетаскиванием и добавить фото кнопкой после последней миниатюры.
- Ограничение загрузки: до 6 фотографий, каждая до 10 МБ; использовать существующее сжатие и проверку файлов.
- Фото открывается в общей галерее/lightbox. Стрелки, закрытие и масштабирование располагать рядом с изображением внутри ограниченной области, а не у дальних краёв экрана.

## Витрина и данные пользователя

- Публикация экземпляра на витрине — явное действие владельца. Публичные данные формировать по разрешённому набору полей; не раскрывать личные цену и дату покупки, приватные заметки, email и другие служебные данные.
- Не смешивать личные изменения экземпляра с общими данными каталога: например, регион экземпляра не должен менять издание для всех пользователей.
- У автора показывать рейтинг и на карточке витрины, и при открытии опубликованного экземпляра, используя общий компонент.
- Лайки и комментарии связывать с пользователем и опубликованным экземпляром; ограничения доступа и удаления проверять на сервере. Повторный запрос не должен создавать дубликаты лайков.
- Не допускать потери порядка фотографий или частичного сохранения связанных изменений.
- Коллекция должна быстро открываться повторно в одной сессии: сохранять данные между маршрутами, обновлять после изменений и сбрасывать при смене пользователя. Не загружать весь каталог ради нескольких экземпляров.
- Сохранять единую модель статуса через `statusId` и справочник `Status`; не вводить параллельные источники статуса.
- Деньги форматировать для `ru-RU`, сохранять копейки; отсутствующее значение не приравнивать к нулю. При работе с API соблюдать принятую сервером модель денежных единиц.

## Проверки и база данных

- Подбирать проверки по затронутому поведению. Для простых изменений текста или CSS не создавать тесты, повторяющие реализацию.
- Основные команды из корня: `npm run typecheck`, `npm run typecheck:server`, `npm run build`, `npm run build:server`, `npm run build:all`. Запускать только относящиеся к изменению, сверяясь с актуальным `package.json`.
- Для серверных изменений и данных запускать релевантные существующие тесты. Проверять авторизацию, сохранение и обработку ошибок, если они затронуты.
- Тесты с БД запускать только на изолированной тестовой базе. Соблюдать существующие предохранители `CI=true` и имя базы `discvault_ci`; не направлять тесты на production.
- Для Prisma использовать предусмотренные команды генерации, валидации и миграций. Не менять уже применённые миграции: добавлять новую.
- Не удалять и не пересоздавать production-базу, не запускать сброс/seed поверх пользовательских данных. Разрушительные операции требуют отдельного явного разрешения.

## Публикация

- Перед публикацией проверить состав diff и выполнить необходимые проверки. Не включать локальные макеты и временные файлы случайно.
- Источник процедуры — `.github/workflows/deploy.yml` и `deploy/auto-deploy.sh`. Отправка в `main` запускает развёртывание; учитывать это до push.
- Для изменений схемы использовать предусмотренный workflow с `apply_migrations=true`, предварительно изучив миграцию. Сохранять этапы резервного копирования, репетиции миграции и проверки здоровья.
- Не запускать дублирующие production-развёртывания. Не прерывать активное переключение сервисов без явного разрешения; сначала изучить этап и журнал запуска.
- После запуска следить за workflow до завершения, разбирать ошибки и исправлять их в пределах согласованной задачи. Успех сборки сам по себе не подтверждает успешное развёртывание.
- После релиза проверить доступность сайта и относящихся к задаче API/функций. В ответе различать подтверждённые проверки и то, что проверить не удалось.
- Номера запусков, временные адреса и хеши релизов хранить в отчёте о задаче, а не в постоянных правилах этого файла.

## GitHub Actions: наблюдение и ошибки

- В проекте настроен GitHub Actions. Основной workflow — `Check and deploy DiscVault` (`.github/workflows/deploy.yml`): job `check` проверяет код и миграции на изолированной БД; job `deploy` зависит от него и публикует только `main`. Для pull request выполняются проверки без публикации. Ручной запуск поддерживает `apply_migrations` (по умолчанию `false`).
- Остальные workflow в `.github/workflows/` обслуживают отдельные операции с данными. Не запускать их вместо основного развёртывания и не считать их успешное завершение подтверждением релиза.
- Для диагностики использовать доступный GitHub-инструмент либо авторизованный `gh`. Репозиторий определять по текущему remote. Примеры команд: `gh run list --workflow deploy.yml --limit 5`, `gh run view RUN_ID`, `gh run view RUN_ID --log-failed`, `gh run watch RUN_ID --exit-status`. Подставлять фактический ID нужного запуска; не выводить токены и секреты.
- Перед разбором сверить workflow, ветку, SHA коммита и причину запуска. Проверять именно запуск с согласованными изменениями. Успешный workflow может пропустить публикацию устаревшего коммита на шаге `Skip commits superseded on main`; в этом случае найти и проверить запуск актуального `main`.

При ошибке действовать последовательно:

1. Найти первый упавший job и шаг, прочитать его журнал и контекст перед ошибкой. Различать ошибку кода/теста, временный сбой инфраструктуры, отсутствие конфигурации и проблему production-развёртывания.
2. Если упал `check`, воспроизвести относящуюся к ошибке команду локально в подходящей среде, исправить причину и повторить релевантные проверки. Не отключать тесты, проверки типов или предохранители ради зелёного статуса. Исправление кода отправлять новым коммитом: повтор старого запуска не подхватит новый код.
3. Повторять тот же запуск без изменения кода только при подтверждённом временном сбое и после проверки, что повтор безопасен и коммит ещё актуален. Пример: `gh run rerun RUN_ID --failed`. Не делать бесконечных повторов без новой диагностики.
4. Если упал `deploy`, установить, дошёл ли запуск до `Transfer and deploy` и строки `Starting remote deployment`. После начала удалённого развёртывания или потери SSH-соединения сначала проверить фактическое состояние сервера: удалённый процесс может продолжать работу. Проверить доступность сайта/API, контейнеры и журналы, состояние миграций и результат восстановления — в зависимости от этапа сбоя.
5. Сообщение о новых миграциях и требовании `apply_migrations=true` означает остановку защитой. Изучить миграции и выполнить предусмотренный ручной запуск для актуального `main` с этим параметром в рамках разрешённой публикации. Обычный rerun не изменяет параметры исходного запуска.
6. При ошибке миграции или сообщении `Schema change was attempted` изучить журнал Prisma и сохранённые файлы восстановления. Не запускать автоматическое восстановление БД, сброс схемы или слепой повтор миграций. Откат образов не отменяет изменения схемы; разрушительное восстановление отдельно согласовывать.
7. Ошибки SSH, secrets, места на диске или блокировки другого deployment исправлять по конкретной причине. Не отключать проверку SSH host key, не удалять резервные копии/volumes и не снимать блокировку действующего процесса ради повторного запуска. Если нужны недоступные права или настройки, сообщить точное препятствие без раскрытия секретов.
8. После исправления дождаться завершения нужного workflow и проверить сайт и затронутые API. В итоговом ответе дать ссылку на запуск, указать результат и подтверждённые проверки; если публикация не завершена, прямо это обозначить.
